# agent-relay — Deep review (2026-09-11)

Phạm vi: toàn repo @ `f25383d` (v0.4.0). Mọi lỗi P0/P1 bên dưới đều đã được
**tái hiện thực tế** bằng script chạy trên bản copy của `scripts/`, không phải

---

## 0. Định vị

Repo này **không phải** một orchestrator. Nó là 3 thứ ghép lại:

1. **Một protocol bằng văn bản** (`skills/*.md` + `docs/file-conventions.md`) —
   quy ước tên file, run-id, và thứ tự stage implement → self-review → cross-review.
2. **Một installer bash** (`bin/`) copy protocol đó vào 4 thư mục skill global.
3. **Một mini state-machine bash** (`scripts/task-*.sh`) cho chế độ parallel.

Giá trị thật nằm ở (1). Rủi ro thật nằm ở (3). Phần (2) là phần chín nhất.

**Điểm mạnh nổi bật:** README trung thực đến mức hiếm gặp — mục *"What this is
not"* và *"Honest limits"* nói thẳng rằng repo không chứng minh được cross-review
bắt thêm bug, không cưỡng chế được việc đổi tool, và `mdc-flat` là dead code.
Đây là thứ nên giữ bằng mọi giá. Phần lớn repo "AI workflow" cùng loại đều
overclaim.

Điểm mạnh kỹ thuật khác: `targets.conf` khai báo (thêm tool = thêm 1 block);
bash 3.2 compat có chủ đích; không sudo, chỉ ghi trong `$HOME`; release từ chối
ref trôi nổi (`main`/`master`) và bắt buộc `--sha256` cho commit SHA — an toàn
hơn đa số installer `curl | bash`; `sync-bootstrap.sh --check` trong CI là giải
pháp gọn cho vấn đề code nhúng bị drift.

## 1. P0 — Lỗi nghiêm trọng, đã tái hiện

### P0-1. Steal stale lock KHÔNG atomic → hai agent cùng sở hữu một task

`task-claim.sh` claim bằng `mkdir` (đúng, atomic). Nhưng nhánh steal lock quá hạn
làm `rm -rf "$LOCK_DIR"` rồi `mkdir "$LOCK_DIR"` — hai thao tác, không phải một
critical section. Agent B có thể `rm -rf` đúng cái lock mà agent A vừa tạo xong.

Repro (40 lần, lock giả đặt epoch 2020):

```
trials where BOTH claimants succeeded: 1 / 40
```

→ ~2.5% cơ hội hai sub-agent cùng nhận `exit 0` trên **cùng một task**. Điều này
trực tiếp phủ định dòng trong `docs/file-conventions.md`:

> | Multiple sub-agents, same `<id>`, same task | No — second claim fails loudly |

Nó cũng là failure mode tệ nhất có thể: không lỗi, không cảnh báo, hai agent ghi
cùng bộ file.

**Fix tối thiểu (giữ nguyên hành vi):** bọc toàn bộ đoạn *check-stale → rm →
mkdir* bằng chính một mutex `mkdir`:

```bash
STEAL_LOCK="$PLAN_DIR/.lock-steal-$TASK_ID"
if mkdir "$STEAL_LOCK" 2>/dev/null; then
  trap 'rmdir "$STEAL_LOCK" 2>/dev/null' EXIT
  # ... re-check age, rm -rf, mkdir, ghi owner ...
  rmdir "$STEAL_LOCK"; trap - EXIT
else
  echo "another agent is stealing this lock" >&2; exit 1
fi
```

**Fix tốt hơn:** bỏ auto-steal. Cho `claim` fail và in hướng dẫn
`task-claim.sh steal <id> <task> <tag>` — một hành động có chủ đích của con
người. Auto-steal sau 2 giờ là chính sách, không phải cơ chế, và nó đang được
cài đặt ở tầng sai.

### P0-2. Path traversal → ghi file tùy ý ngoài repo

`report-write` không validate `<task-id>`:

```bash
echo pwned | ./task-claim.sh report-write z ../../../../../../tmp/AR-PWNED -
# -> /tmp/AR-PWNED.md  (ghi thành công)
```

`claim`/`update` bị chặn một phần vì đòi `<task-id>.status` tồn tại, nhưng
`.lock-$TASK_ID` thì vẫn theo traversal.

Đây không phải lỗ hổng lý thuyết: `<task-id>` **do LLM sinh ra khi parse file
plan**, mà file plan có thể đến từ issue, PR, hay repo của người khác. Đó là
đường từ nội dung không tin cậy tới arbitrary file write.

**Fix:** validate cả `<id>` và `<task-id>` ngay đầu mỗi subcommand:

```bash
case "$TASK_ID" in
  ''|.|..|*/*|*'\'*) echo "Error: invalid task id" >&2; exit 1 ;;
esac
[[ "$TASK_ID" =~ ^[A-Za-z0-9._-]+$ ]] || { echo "Error: invalid task id" >&2; exit 1; }
```

### P0-3. `task-init.sh` mất task **im lặng** khi plan thiếu heading `## Tasks`

Khi không có `## Tasks`, parser fallback quét **toàn bộ** file; mà markdown
đánh số lại từ 1 ở mỗi list, nên `T<n>` bị trùng và ghi đè lẫn nhau.

Repro:

```markdown
## Goal
1. Ship it
## Notes
1. Be careful
```
```
Initialized ... with 2 task(s).      <- đếm 2
- [pending] T1: Be careful           <- chỉ còn 1 task, và là task SAI
- [pending] T1: Be careful           <- .order trùng, rollup in 2 lần
```

Task "Ship it" biến mất hoàn toàn. `found_count` vẫn báo 2. Không có cảnh báo.
Đây là mất dữ liệu ở đúng bước đầu tiên của pipeline — mọi stage sau đều review
một tập task đã sai.

**Fix (3 phần):**
- Task id = bộ đếm tuần tự toàn cục, **không** dùng số của markdown list.
- Refuse (không phải overwrite) khi `<tid>.status` đã tồn tại.
- Fail rõ ràng nếu không tìm thấy `## Tasks`, thay vì fallback quét cả file.
  Fallback hiện tại cũng sẽ nuốt số thứ tự trong phần Constraints/Goal.

---

### P0-4. Cú pháp `update --session` trong tài liệu là **sai**

`--session` chỉ được parse **trước** subcommand. Nhưng usage string của chính
script, và `docs/file-conventions.md`, đều ghi:

```
task-claim.sh update [--session <tag>] <id> <task-id> ...
```

Chạy đúng như tài liệu:

```
$ ./task-claim.sh update --session agentA z T1 done
Error: plan directory '.agent-relay/implement-plan---session' does not exist.
```

`--session` bị nuốt làm `<id>`. Skill text dạy agent dùng dạng positional nên
chưa nổ trong thực tế, nhưng tài liệu đang mô tả một giao diện không tồn tại.

**Fix:** cho phép `--session` ở cả hai vị trí, hoặc sửa usage + docs. Nên làm cả hai.

## 2. P1 — Đáng sửa trước bản release sau

| # | Vấn đề | Bằng chứng / tác động |
|---|---|---|
| P1-1 | `release` **không** kiểm tra owner | Agent B chạy `release z T2` rồi `claim z T2 agentB` → cướp lock của A, exit 0. Mutual exclusion chỉ còn là quy ước. |
| P1-2 | Ownership fallback về biến môi trường `$SESSION` / `$SESSION_TAG` | `SESSION=agentA ./task-claim.sh update z T2 done` → exit 0. Biến môi trường ambient quyết định quyền ghi. Bỏ hai fallback này. |
| P1-3 | Status enum không validate | `update z T1 a1 bogus-status` → ghi thẳng `status: bogus-status`. Phá contract mà 2 skill review đang đọc. Whitelist `pending\|in-progress\|done\|skipped`. |
| P1-4 | `skipped` dep khóa chuỗi vĩnh viễn; cycle không bị phát hiện | T1 `skipped` → T2 không bao giờ claim được, không có `--force`. T1↔T2 cycle → cả hai block mãi, không báo cycle. Với agent tự chạy đây là vòng lặp "hết task" không giải thích được. |
| P1-5 | `sort -V` không có trên BSD/macOS sort cũ | `done \| sort -V 2>/dev/null \|\| true` — nếu `sort -V` fail, `\|\| true` **nuốt lỗi** và `get_ordered_tasks` trả về **rỗng** → `list` rỗng, rollup rỗng, im lặng. Dùng `sort` thường + zero-pad hoặc `sort -t T -k2,2n`. |
| P1-6 | **CI không chạy `tests/tasks.sh`** | `ci.yml` gọi `sync-bootstrap --check`, `smoke.sh`, `smoke-remote.sh` — thiếu `tasks.sh` (chỉ `make smoke` mới có). Đây chính là lý do P0-1…P0-4 sống sót. README còn khẳng định *"CI checks the installer and the task scripts"* — không đúng. |
| P1-7 | Không có `shellcheck` trong CI | 3.600 dòng bash, quote/traversal/`local` trong pipeline. Một job shellcheck là ROI cao nhất trong repo này. |

## 3. P1/P2 — Thiết kế Skill (phần chuyên môn)

### 3.1. Skill bị cắt rời khỏi tài liệu của chính nó — vấn đề lớn nhất về mặt skill design

Format `skill-folder` cho phép cài **cả thư mục** (`references/`, `scripts/`).
Installer hiện chỉ copy đúng `SKILL.md`. Hệ quả là mỗi skill phải tự thú nhận:

> The same rules are in the agent-relay repo at `docs/file-conventions.md`;
> that file **is not installed next to this skill**.

Và vì thế quy tắc run-id bị **copy-paste 3 lần** trong 3 file skill. Đó là nguồn
drift được lập trình sẵn — sửa quy ước một chỗ, hai chỗ kia lệch.

**Fix (đúng chuẩn progressive disclosure của Agent Skills):**

```
~/.claude/skills/atry-implement/
├── SKILL.md                        # ngắn: khi nào dùng, gọi gì
├── references/file-conventions.md  # đọc khi cần chi tiết
└── scripts/task-claim.sh           # agent gọi trực tiếp, path tương đối
```

`SKILL.md` chỉ còn *"Run-id rules: đọc `references/file-conventions.md`"*.
Bonus: `resolve-task-bin.sh` và toàn bộ cơ chế `~/.agent-relay/scripts/` +
override `.agent-relay/scripts/` trở nên **không cần thiết** — script nằm ngay
cạnh skill. Bỏ được một lớp indirection và một failure mode ("older release
tarballs may lack these scripts").

### 3.2. Thiếu stage 1 (plan)

Chain 4 bước nhưng bước 1 không có trong repo. Hệ quả kéo theo: header
`base:`/`id:` phải do người dùng nhớ gõ, và `task-init.sh` phải parse markdown
tự do (→ P0-3). Một skill `atry-plan` sinh plan đúng schema + set `CURRENT` sẽ
**xoá cả lớp lỗi parse**, vì plan khi đó do chính hệ thống sinh ra.

### 3.3. Ngày tháng do model tự nghĩ ra

Cả 3 skill đều nói *"Use today's date: YYYY-MM-DD"* nhưng **không** bảo agent
chạy `date`. Model đoán ngày sai là chuyện thường ngày. Mà toàn bộ logic
*"replace only that day's section"* của `atry-self-review` phụ thuộc vào việc
heading ngày khớp chính xác. Sai ngày → không replace được → section trùng lặp.

Fix một dòng, thêm vào cả 3 skill:

```bash
TODAY="$(date +%F)"   # dùng giá trị này, không tự đoán ngày
```

### 3.4. Giao thao tác markdown tinh vi cho LLM

> *"replace only that section (from its heading to the next `## ` heading or EOF)"*

Đây là thao tác dễ hỏng nhất mà một LLM có thể được giao: đọc file, tìm ranh
giới section, ghi lại nguyên vẹn phần còn lại. Rủi ro nuốt mất section
`## Cross-Review` là có thật, và mất nó thì mất luôn output của stage tốn kém
nhất.

Repo đã có triết lý đúng cho `task-claim.sh` — áp dụng tiếp:
`review-section.sh upsert <file> "Self-Review" "$TODAY"`. Deterministic, test
được, và giảm token.

### 3.5. Không có provenance — giả thuyết cốt lõi không kiểm chứng được

Toàn bộ luận điểm của repo là *"reviewer thứ hai ở model/tool khác bắt được lỗi
model đầu bỏ sót"*. Nhưng không có gì ghi lại **tool/model nào đã chạy stage
nào**. README thừa nhận điều này ở mục Limits, nhưng nó không chỉ là hạn chế —
nó khiến giả thuyết trung tâm không thể kiểm chứng, và khiến câu *"There is no
measured result"* trở thành vĩnh viễn.

Chi phí để sửa gần như bằng 0: mỗi skill append một dòng vào đầu section của nó.

```markdown
## Cross-Review — 2026-09-11
<!-- relay: tool=claude-code model=<id> base=<ref> -->
```

Không cưỡng chế được (nothing ever will), nhưng biến việc kiểm tra từ *không thể*
thành *nhìn là thấy* — và mở đường cho việc đo lường thật sự về sau.

### 3.6. Cross-review vừa review vừa sửa code

`atry-cross-review` được phép *"fix confirmed bugs directly"*. Nghĩa là phần sửa
của reviewer cuối cùng **không ai review**. Với stage được quảng cáo là "bắt cái
mà model cùng họ bỏ sót", đó là điểm mù ngay tại chỗ quan trọng nhất.

Đề xuất: cross-review đánh dấu rõ mọi thay đổi của nó trong một mục riêng
(`### Changes made by cross-review`), và khuyến nghị một vòng verify ngắn sau đó.

### 3.7. `CURRENT` là global mutable state, và bị ghi quá sớm

Cả 3 skill đều được lệnh *"After resolving an id, write/overwrite `CURRENT`"* —
kể cả khi chỉ **đọc** id có sẵn. Chạy self-review cho feature B sẽ cướp `CURRENT`
của feature A đang dở. `docs` gọi đây là "soft conflict", nhưng nó phát sinh từ
một lựa chọn dễ đảo: **chỉ ghi `CURRENT` khi tạo id mới**, không ghi khi resolve.

### 3.8. Khác

- Descriptions trong frontmatter khá tốt (đều có mệnh đề *"Use when…"*, 234–345
  ký tự) — đúng hướng cho việc trigger.
- Tiền tố `atry-` không được giải thích ở bất kỳ đâu trong repo.
- Không skill nào có guard "phải ở trong git repo", dù cả 3 đều giả định `git diff`.

## 4. P2 — Ghi chú nhỏ

- `source "$CONF"` nghĩa là `targets.conf` từ tarball tải về được **thực thi**
  như bash. README đã nói checksum không phải chữ ký; nên nói thẳng thêm rằng
  đây là RCE surface nếu release bị thay.
- `mdc-flat` là dead code (README thừa nhận). Dead code không test = sẽ hỏng
  lặng lẽ. Xoá, hoặc thêm test.
- `resolve_paths()` đoán base dir qua `[[ -f "CURRENT" ]]` trong cwd — chạy từ
  subdirectory của project sẽ tạo `.agent-relay/` mới ở sai chỗ. Nên đi ngược
  lên tìm marker giống `git rev-parse --show-toplevel`.
- Rollup lock tự steal sau ~5s (100 × 50ms). Con số tuỳ tiện; trên NFS/FS chậm
  với plan lớn là quá ngắn.
- File rollup `implement-plan-<id>.md` vừa là "generated, read-only" ở chế độ
  parallel, vừa là file nguồn hợp lệ ở chế độ sequential. Cùng tên, hai ngữ
  nghĩa. `task-init` refuse khi thấy nó là xử lý đúng, nhưng tên file nên khác
  nhau giữa hai chế độ.

## 5. Thứ tự đề xuất

1. **Gắn `tests/tasks.sh` + `shellcheck` vào `ci.yml`.** Làm trước tiên — nó là
   lý do 4 lỗi P0 đi lọt.
2. Vá P0-2 (validate id) và P0-3 (task-init) — rẻ, tác động lớn.
3. Vá P0-1 (steal lock) và P0-4 (docs/`--session`).
4. P1-1…P1-5 (ownership, enum, deps, `sort -V`).
5. Đóng gói skill đúng chuẩn: `references/` + `scripts/` trong skill folder
   (§3.1) → bỏ được `resolve-task-bin.sh`.
6. Thêm `atry-plan` (§3.2) và provenance line (§3.5).
7. Sửa README: câu *"CI checks … the task scripts"*, và đổi nhãn parallel mode
   từ "experimental" sang có bảo hành sau khi P0 được vá.

Cho đến khi P0-1 và P0-3 được vá, khuyến nghị: **chỉ dùng chế độ sequential**,
hoặc parallel với một git worktree riêng cho mỗi agent.
